# Proposal and execution authority

Use this before mission/task creation, project selection, spawning a newly
authorized outcome, or treating an approval as permission to implement.

## Classify authority

1. Identify the exact verb, object, and current conversational referent.
2. Proposal verbs—decide, explore, research, recommend, scope, compare,
   discuss, or choose priorities/architecture—authorize only a concise chat
   proposal. They cause zero mission, task, attempt, workspace/project
   mutation, Git, lease, worker, or notification effects.
3. Execution requires an explicit implementation verb plus object, or an
   explicit approval whose clear referent is the concrete proposal and an
   explicit pending start question. A named autonomous build is sufficient;
   ceremony is not required.
4. Mixed language without a clear implementation verb/object gets one concise
   confirmation before every effect. General conversational assent and
   scope-choice permission are not implementation authority.
5. Authority applies only to the named outcome and never becomes standing
   permission for follow-on tasks, publication, remote/resource creation,
   delivery, merge, destructive action, or another project.

## Select the project

List the commander's attached Sophon workspace projects. Choose by explicit
project key first, then a single clear current referent. When two or more
projects plausibly match, ask one concise project question and stop before
records or effects. Never use the process current directory as hidden project
authority. A project-specific inspection resolves that exact child and labels
the reply `Project <key>:` even when no mission/task exists; an unlabeled
global status is not an answer to a selected-project request.

For cross-project outcomes, preserve one commander outcome in conversation and
create project-confined missions/tasks for each implementation seam. Workers
must never receive an unconstrained multi-repository checkout.
